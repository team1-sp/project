# Model Compatibility Notes

The docs in this repository must work for strong and weak models, long- and short-context models, with and without code execution, in any tool. This file defines how to *write* docs for that, and how to *read* them safely.

## Writing conventions (apply to every doc)

1. **Plain Markdown only.** Headings, lists, tables, fenced code blocks. No HTML, no images carrying information, no tool-specific syntax (`@file`, slash commands, MCP names).
2. **Explicit over implicit.** Write "MUST NOT call the physics library directly" instead of "keep physics decoupled".
3. **Short files, stable paths.** < ~400 lines per file; link by relative path. Do not rename files casually — other docs and agents link to them.
4. **Greppable.** Put exact error strings, component names, IDs and keywords in text, not only in screenshots. Entry headings follow `### ID — Title`.
5. **State certainty.** Tag claims `[VERIFIED]`, `[ASSUMPTION]`, `[TBD]`, `[PROPOSED]`. Tags are labels, not a substitute for asking: a material uncertainty must also be put to the human (`DECISION NEEDED`).
6. **Examples beat prose.** Show the exact command, the exact entry, the exact file layout.
7. **No hidden context.** Never write "as discussed" or "see earlier conversation". If it matters, it is in a file.
8. **Tool-neutral commands.** Write the command to run (`cmake --build build`), not "click Run in the IDE". The build system is not decided yet (Q-009); until chosen, reference `environment-setup.md`.

## Reading conventions

| Situation | Behaviour |
| --- | --- |
| Limited context window | Read in the boot order from `agents/README.md`; stop after step 6 and only open task-relevant docs. Use search (grep) on `history/*` instead of reading them whole. |
| Cannot execute code | Say so in the task and handoff. Do static work (design, tests-as-code, docs). Never write "tests pass". |
| Cannot write files in the repo (chat-only model) | Output complete file contents with the target path as a heading so a human can paste them; also output the exact handoff entry text. |
| Cannot access the internet | Do not assume library APIs; mark `[ASSUMPTION]`, flag for verification. |
| Weaker model / unsure about a step | Follow `AGENT-PROTOCOL.md` checklist items literally; prefer the playbooks in `playbooks/`; choose the smaller task. |
| Doc is long or confusing | Don't guess. Add a `Q-###` or fix the doc (doc-keeper hat) in a separate task. |

## Verifying your own claims

- Library function names, versions, flags: check the repo's dependency file or the vendor docs; otherwise tag `[ASSUMPTION]`.
- File existence: list the directory; do not assume from memory of an earlier session.
- "It works": quote the command and its output summary.
- Numbers (FPS, timings): state hardware and mode (normal/headless) — the performance targets are defined on "reference hardware", which is not defined yet (ask the human).

## Style of agent output into the repo

- Concise. A task result is a paragraph, not an essay.
- No emojis in docs. No marketing language.
- Use the glossary terms. Use English.
- Do not add "generated by AI" banners to code; do log AI use for course deliverables (see `guidelines/genai-usage-rules.md`).

## Known model-specific pitfalls (extend this table as you observe them)

| Pitfall | Mitigation |
| --- | --- |
| Hallucinating Box2D / Raylib API names (Box2D v2.4 C++ and v3 C APIs differ greatly; Raylib versions differ) | Check the pinned version in the build/dependency file and the library's own headers; compile before claiming. |
| Resolving uncertainty by guessing and burying the guess | Truth Rule in `AGENT-PROTOCOL.md`: raise it with the human. |
| Treating course documents (Initial Plan) as truth | The decision log is the truth (DEC-017). |
| Over-eager refactoring | Rule P-8; one task one diff. |
| Forgetting append-only rule and rewriting logs | Rule P-6; use the templates. |
| Treating `Proposed` decisions as final | Only `Accepted` binds. |
| Mixing terminology (physics engine vs library vs adapter) | Glossary. |

When you observe a new model-specific failure, add a row here and (if it cost time) a `PRB-###` entry.
